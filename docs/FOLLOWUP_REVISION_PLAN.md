# 결과 수정 요청을 후속 제작으로 연결하는 다음 단계

2026-10-05 재개 **이전** 코드와 SQL을 읽어 정리한 설계 이력이다. 이후 재개하여 API·DB 제안·실행기·화면을 구현했다. 최신 구현과 검사 범위는 [후속 수정 제작 연결](FOLLOWUP_REVISION.md), 최종 진행 상태는 [STATUS](STATUS.md)를 따른다. 운영 적용은 아직 하지 않았다. 아래 “현재 제약”은 구현 전 분석이며 최신 코드 상태를 뜻하지 않는다.

## 목표 동작

교사가 특정 결과에 저장한 수정 요청을 고르면, 원래 과제·출처·대상 후보와 변경 요청을 함께 보여 준다. 정확한 입력과 새 작업 비용을 다시 확인한 뒤 같은 콘텐츠ID의 다음 제작을 접수한다. 기존 실패·검토·후보 기록은 보존하고 새 후보를 다시 검사한다. 새 작업에도 월10건·월10,000원·작업당1,000원·동시1·최대9호출·자동 수정2회 제한을 적용한다. 메모 저장만으로 새 작업이나 게시를 시작하지 않는다.

## 구현 순서와 경계

1. **부모 참조와 입력 계약**: 브라우저는 부모jobId·feedbackId·현재 결과 버전·새 clientRequestId만 보낸다. 원래 입력과 후보 바이트는 서버의 검증된 결과에서 가져온다. 다른 사용자의jobId, note종류 의견, 다른 후보/증거/상태 버전, 후보 없는 결과를 거부한다. 원래 과제와 수정 지시를 명확히 구분하여 전부 확인 화면에 표시한다. 학년도 입력을 다시 만들지 않는다.
2. **불변 참조 저장**: 새 입력은 작은 부모 참조(원래 sourceHash·candidateHash·evidenceHash·feedbackId/본문 해시)를 포함한다. 별도의 콘텐츠 소유권/작업 계보와 현재 접수 버전을 둬 같은ID의 중복/오래된 부모 분기를 막는다. 기존 입력·작업을 다시 쓰지 않고 신규용unique를 별도조건으로 보존한다. 부모 후보 참조와동의는 모두sourceHash에 결합한다.
3. **새 동의와 원자 접수**: 준비/조회는 유료 예약을 만들지 않는다. 승인과접수 시 부모 버전·피드백·콘텐츠 소유권·계보 head를 다시 확인한다. 같은 요청 재전송은 같은 자식job을 반환하며 다른내용/다른클릭ID로 같은피드백을 이중 실행하지 않는다. 예산→교사→대화→콘텐츠계보→작업/worker→입력 순서를 기존잠금과 함께 검토하고 순환을 없앤다. 취소/대화삭제·교사비활성·정책비활성 경쟁도포함한다.
4. **부모 후보 전달**: 자식에게 결합된 부모만 서비스가 읽어 주고 OIDC의현재 작업/역할/실행번호 권한을 확인한다. 후보파일은 허용목록·해시/크기를 재검증하며 관리origin이나제작프로세스에서 실행하지 않는다. 기존 승인입력50KB와호출150KB/24,000token 상한은 유지한다. 초기 구현은 전체부모후보와지시가 모델문맥에 들어가는 경우만지원하고, 넘으면 어떤자료도 자르지않고 명시적 보류한다. 바이트사전검사는 유료역할호출 전, 토큰검사는 기존한도 경로를 사용한다.
5. **제작·검사·결과 연결**: 기존5역할 검토·실행 검사·예산·최대2회 자동수정은 유지한다. 초기 developer 입력에 검증한부모후보와수정지시를 포함하고 ID/grade/unit/revision을보존한다. 새후보의과학/학습/실행검사를다시생성하며 부모의pass/승인을복사하지 않는다. 결과화면은 부모/현재버전과각실패이력을연결한다. 사람의게시승인은별도다.

계보의 head는 “마지막으로접수한작업”과 “수정기준이되는후보”를 구분해야 한다. 새작업이실패/취소됐다고과거부모를몰래최신으로되돌리거나재접수하지않는다. 실패뒤재시도는현재계보와정확한기준후보를표시한새확인/비용동의로처리한다. 이 상태전이와 잠금순서를 테스트사례로먼저고정한뒤 SQL을작성한다.

## 필요한 검증

- 실제 해시를 사용해 원래 입력/후보/수정 요청의 연결, 다른 소유자·변조·오래된 버전·본문 누락·크기 초과를 거부한다. 큰 후보를 잘라 통과시키지 않는다.
- PGlite로 동의 전 미접수, 입력/예산/계보 원자성, 응답 유실 뒤 같은 자식 반환, 월 한도와 불확실 비용 보존, 취소와 정책 비활성을 검사한다.
- 새 PostgreSQL17에서 같은/서로 다른 clientRequestId의 동일피드백 경쟁, 같은부모의다른수정요청경쟁, 자식완료와오래된부모접수, 대화삭제/취소경쟁을 실제 별도연결로 확인한다. 테스트는 폐기 가능한 로컬DB에서만 하며 종료/PID/임시암호 정리까지 확인한다.
- UI의 전체 전달내용 확인·새 비용동의·중복클릭·새로고침복원·버전충돌 안내·390/1440px·키보드/axe·생성코드 비실행을 확인한다. 수정 전후의학습/과학/런타임판정을혼동하지않게 표시한다.
- 모의 모델과 실제 검사를 구분하여1회 후속제작 왕복을 확인하고, 실제 OIDC/Linux격리/유료호출·운영적용은 별도 단계로남긴다.

구현 파일과 새 SQL 제안은 미스테이징으로 만들고 기존40개 스테이징을 보존한다. 공개 업로드의 구체적 범위 승인과 API키 질문은 이미 대기 중이다. 새 사용자 중단 기준은 남은 약20%이며 약25%부터 정리하여20% 전에 멈춘다.
