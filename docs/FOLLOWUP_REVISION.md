# 후속 수정 제작 연결

2026-10-05 로컬 구현. 운영 SQL·기능 플래그·원격 작업은 아직 적용하지 않았다. `STUDIO_REVISION_ENABLED=false`가 기본이며 입력/결과 기능도 준비되어야 화면을 사용할 수 있다.

## 교사 흐름

결과에 버전이 결합된 수정 요청을 저장하고 “이 요청으로 수정 준비”를 선택한다. 기존 과제·누적 수정 요청·같은 콘텐츠ID·기준 후보·자료 요약과 새 비용을 확인한다. 입력 사용 범위와 별도 제작 1건의 비용에 동의한 뒤 시작한다. 준비/의견 저장만으로 비용 예약이나 모델 호출을 시작하지 않는다.

수정에도 월10,000원·월10건·건당1,000원·동시1·최대9호출·작업당20분·자동 보완2회가 적용된다. 후속 제작은 콘텐츠당20세대까지다. 실제 청구액은 내부 환율/세금 추정과 다를 수 있다. 실패/중단 전 발생한 비용과 불확실 비용 예약은 기존 장부 규칙대로 남는다.

브라우저에는 복원용 입력ID·요청UUID·의견ID만 저장한다. 확인하지 않은 체크박스 상태는 새로고침으로 복원하지 않는다. 서버가 이미 접수한 뒤 응답만 유실되면 같은 작업을 조회하며 새 제작을 자동 접수하지 않는다. 새 결과에서 수정 전 작업으로 이동할 수 있다. 생성 파일은 관리 화면에서 실행하지 않는다.

## 원래 결과와 동의 경계

- 브라우저의 준비 요청은 부모 작업ID·수정 의견ID·정확한 상태/입력/후보/증거 버전·새 요청UUID만 보낸다. 서버가 부모의 원본 입력과 저장된 개발자 출력에서 기준 후보를 가져와 다시 검사한다.
- 원래 과제·자료·맥락·기존 요구사항은 그대로 보존한다. 마지막 요구사항에 해당 의견을 추가하고, 부모/피드백/계보 head와4개 버전값·기준 출력의 바이트 해시를 입력 해시에 포함한다.
- 기존 작업/후보/실패/검사/예산 행을 다시 쓰지 않는다. 별도 입력에 전체 기준 후보를 저장하고 수정 작업에만 결합한다. 준비한 입력의 sourceHash에 동의하며 준비/동의/접수마다 계보를 재검증한다.
- `content_heads`의 head는 마지막으로 **접수한 작업**이다. 같은 부모의 다른 요청이 먼저 접수되면 나머지는 오래된 입력이 된다. 후속 작업이 후보를 하나라도 만들었다면 그 결과를 검토하고 그 버전에서 수정해야 한다.
- 후속 작업이 후보 없이 종료했고 비용이 확정되어 닫힌 경우에만 원래 후보로 새 의견·새 동의를 받아 재시도할 수 있다. 소비한 의견은 다른 요청UUID로 다시 실행할 수 없다. 원래 같은 요청UUID의 응답 복원은 기존 영수증을 반환한다.

`studio_revision_v1.sql`은 result/input/dispatch 제안 이후의 검토용 증분이다. 서비스 전용 RLS 테이블, 제한된 열 권한, security invoker/빈 search_path를 사용하며 브라우저 역할에는 테이블/함수 권한이 없다. 승인 RPC의 잠금 순서를 예산→교사→대화→입력으로 맞추고, 그 전역 예산 잠금 안에서 부모/worker/head를 잠근다. 기존 소비 trigger와 새 head trigger가 작업·입력·예산·dispatch intent의 전체 트랜잭션을 함께 성공 또는 취소시킨다. SQL은 운영 migration으로 등록하거나 적용하지 않았다.

## 후보 전달과 새 검사

승인 입력은 기존50,000bytes 상한을 유지한다. 전체 기준 후보는 별도 저장하고 해시로 결합한다. generation 역할의 현재 작업·OIDC 실행번호/attempt/sourceHash가 일치하는 경우에만 입력 응답에 전달한다. report 역할이 이 경로로 부모 소스를 읽거나 generation 역할이 실행 검사 결과를 쓰는 것은 허용하지 않는다.

부모 후보를 허용 파일·메타데이터·후보 해시로 재검증한다. 준비 시 `{input, context, previousCandidate}`가110,000bytes를 넘으면 명시적으로 보류한다. 고정 규격과 설계 의견에40KB를 남기기 위한 사전 제한이며 입력을 자르지 않는다. 실제 호출마다150,000bytes·24,000입력tokens를 다시 검사한다. 새 후보가 커져 이후 독립 검토 입력이 한도를 넘는 경우에도 호출을 중단하고 이전에 발생한 비용은 남는다. 사전 크기 검사만으로 모든 후속 호출이 들어간다고 보장하지 않는다.

첫 개발자는 정확한 이전 후보와 새 요구를 받는다. 검토자는 원래 요구·새 요구·새 후보·별도 실행 결과와 이전 후보를 비교한다. 교육과정/교과·설계/개발/독립검토의5개 컨텍스트와 매 후보의 별도 실행 검사, 자동 보완2회 상한을 유지한다. 부모의 통과 의견·실행 결과·게시 승인을 새 결과에 복사하지 않는다. 게시 적격은 여전히false이며 신뢰할 수 있는 원문 검토·배포물·승인·게시 확인 연결이 남았다.

## 검증 현황

- 초기 후속수정6개와 기존 입력/파이프라인 검사는 통과했다. 서명된 로컬 HTTP→PGlite→합성 모델5회→별도 보고자→새 결과→다음 수정 준비 왕복도 통과했다. 실제 유료 AI/실제 GitHub OIDC는 아니다.

- 제작실 전체151/151 PASS/exit0(85.64초), production build/TypeScript 통과. Chrome 기존17개 통과와 새2/2 재검사 PASS/exit0(16.6초)를 합쳐19개 통과 증거가 있다. 전체 첫 실행은17/19였고 새2개는 숨은 Next 알림을 함께 고른 선택자 오류를 수정했다. 실패 trace는 `.local/evidence/worker/browser-revision-initial-003ec477e57c40a9863076fd527299d1/`에 보존한다. 컨테이너 복사 import4/4 통과이며 실제 Linux Docker 실행은 아니다.
