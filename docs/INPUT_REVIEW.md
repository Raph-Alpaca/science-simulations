# 제작 입력 확인과 버전 결합

2026-10-05 로컬 구현·검사 결과. 운영 DB/앱에 적용하지 않았으며 유료 호출·공개 업로드·게시도 실행하지 않았다.

## 사용자 흐름

제작 입력 기능이 준비된 환경에서는 과제·학년·단원·2D/3D 유형과 최대6개의 공개 참고 링크/직접 작성한 요약을 입력한다. 3D에는 카메라 조작과 대체 설명이 포함됨을 안내한다. 화면에서 제작기에 전달할 정확한 내용과 월10,000원/10건·작업당1,000원·최대2회 수정 조건을 확인한 뒤 입력 사용 범위와 비용 조건을 저장한다.

과제나 자료를 수정하면 화면의 기존 확인과 체크를 해제한다. 동일한 입력의 응답 유실은 같은 요청 ID로 조회할 수 있고 중복 클릭은1회만 처리한다. 브라우저에는 이동/검토 ID와 요청 해시만 저장한다. 과제·요약·키는 브라우저 저장소에 넣지 않으며 로그아웃 시 해당 식별자도 기존 정리 경로에서 제거한다. 새로고침은 서버에서 본인 기록만 다시 읽는다.

입력 준비·확인은 AI나 비용 예약을 시작하지 않는다. 확인된 입력에서 실제 작업을 만드는 RPC까지 구현했으나 브라우저에서 그 RPC를 직접 호출할 수 없으며, 실제 GitHub dispatch 연결 전에는 제작 시작 버튼을 활성화하지 않는다. 기존 모의 작업 UI는 기본 설정에서 유지된다. 입력 확인은 결과물의 검토·게시 승인을 대신하지 않는다.

## 입력과 출처

`input-review.mjs`가 허용 필드만 읽고 독립 명세를 생성한다. 대화 제목/이전 메시지/원문 파일/사용자 권한 필드를 가져오지 않는다. 제목과 콘텐츠 ID는 분리하고 사용자+요청 ID에서 새 `sim-…` ID를 고정해 중복 요청과 다른 사용자의 충돌을 막는다. 기존 콘텐츠 ID/주소를 수정하지 않는다.

출처는 HTTPS 공개 링크, 자료명, 절/쪽/범위와 교사가 직접 작성한 최대900자 요약이다. URL을 자동으로 가져오지 않으며 `teacher_supplied`, `not_independently_verified`를 명시한다. 링크가 있거나 사용자가 자료 사용에 동의했다는 이유로 원문·교육과정·교과서 대조를 통과 처리하지 않는다. 신규 입력은 사용자가 정한 내부2022 개정 기준을 선택하되 검증 상태는unverified이며 학년도는null/입력 없음이다. 과거 입력/해시는 변경하지 않는다. 실제 원문 수집·독립 대조는 남은 실행 단계다. [게시 근거v2와의 구분](EDUCATION_EVIDENCE.md).

권한 필드 추가, 지원하지 않는 제작 유형, 인증 정보 포함 URL, loopback/IP 주소, 알려진 키 형식·비공개 경로, 중복 출처, 상한 초과를 거부한다. 패턴 검사는 모든 개인정보/권리를 증명하는 탐지기가 아니며 입력 사용 확인은 교사가 표시한 범위에 대한 기록이다. HTTP는 기존16KB, 새 입력 API만64KB, 스트림5초 제한이고 정확한 제작 입력은50KB 이내다.

## DB·서버 경계

`studio_input_review_v1.sql`은 worker SQL 다음에 적용할 **미적용 검토안**이다. `input_reviews`는 RLS와 서비스 전용 RPC를 사용한다. anon/authenticated에는 테이블·함수 접근을 주지 않는다. 실제 세션/허용 교사 검증을 통과한 서버가 owner를 지정하며 RPC도 active 교사, 본인 대화와 삭제 상태를 확인한다. [Supabase RLS 공식 문서](https://supabase.com/docs/guides/database/postgres/row-level-security)의 서비스 키 분리와 SQL 권한 원칙을 확인했다.

- prepared→approved→consumed 상태를 사용한다.24시간 이내 확인·접수해야 하며 이미 사용한 영수증 조회는 같은 작업만 반환한다.
- 본문 UTF-8 바이트의 SHA-256, 요청 스냅샷, 콘텐츠 ID, 정확한 동의 버전을 묶는다. 본문/해시/소유자/요청 식별자는 service_role UPDATE 권한도 없다. 동의 내용은 고정 JSON CHECK로 제한하고 작업/소유자는 복합 FK로 맞춘다.
- 새 worker 행은 트리거에서 실제 승인된 기록과 본문/해시/대화/요청을 대조하고1개 작업으로 소비한다. 임의 검토 UUID로 우회하는 경로를 막는다. 앞선 worker 행을 재작성하거나 과거 UUID에 검토 사실을 부여하지 않는다.
- 접수와 기록 소비·작업 예산 예약은 한 트랜잭션이다. 예산 부족 시 작업/소비 상태가 함께 롤백된다. 동일 확인의 중복 접수는 같은 작업을 반환한다.
- 한 교사당24시간30개, 총500개 확인 기록 상한이다.24시간은 접수 유효기간이며 원문 자동 삭제 기간이 아니다. 대화 삭제 뒤에는 API에서 숨기지만 확인 기록은 현재 별도 보존된다. 운영 활성화 전 전체 보존/정리 정책과 함께 검토해야 한다.

기본 `STUDIO_INPUT_REVIEW_ENABLED=false`. true여도 DB의 `input_review_version()`을 확인해야 화면에 준비 기능이 열린다. 기존 작업 실행·예산·OIDC의 비활성 설정은 바꾸지 않는다. Supabase 키는 서버에 남고 Next 클라이언트는 JSON API만 호출한다.

## 검증

전체 제작실125/125 통과, production build와 내장 TypeScript 통과. 새 입력/SQL6개와 본문 스트림2개를 추가했다. 최종 동의 CHECK/소유자 FK 보완 후 입력6개를 다시 통과했다. 입력 저장의 비용0, 동일 입력/서명, 다른 소유자·비활성 교사·삭제 대화·만료, 허위 승인 UUID, 동의 변경/본문 덮어쓰기 거부, 비용 부족의 전부 롤백을 확인했다. 기존 실패 검사를 제거하지 않았다.

실제 Chrome의 새 입력 화면2개(390/1440px), 기존 화면9개 모두 통과했다. 새 화면 검사는 합성 계정의 API 전송을 로컬 서비스 모듈/PGlite SQL로 연결했다. 3D 선택, 상세 요약 미리보기, 두 확인 조건, 중복 클릭1회, 브라우저 원문 저장 없음, 새로고침 복원, 편집 시 재확인, 가로 넘침 없음, axe 위반0을 확인했다. 실제 운영 로그인/원격 API 성공으로 확대하지 않는다. 합성 화면 캡처를 `.local/evidence/worker/input-review-*.png`에 보존하고 직접 확인했다.

새 PostgreSQL17 loopback 클러스터의14개 물리 연결 경쟁 검사 PASS/exit0. 최종00:17:41~00:18:08 KST, `.local/worker-pg17-input-5bd929149b0b4122816e769c2025247b/result.json`. 모든 사례에서 다른 비슈퍼유저 service_role 연결의 Lock 대기와 차단 PID를 관찰했다. 기존11개에 입력 확인→접수, 동일 확인의 중복 접수, 대화 삭제→확인 거부3개를 추가했다. 모든 작업이 실제 입력 확인 기록을 사용한다. 추가 그룹은 별도 검사 DB에서 실행해 기존 월10건 상한이나 불확실 비용 기록을 지우지 않았다.

6개 SQL 해시 일치, stopped=true, postmaster.pid/임시 평문 암호 없음, 현재 사용자/SYSTEM 전용 ACL 확인. 보완 전14개 결과도 별도 보호 폴더에 보존했다. 운영 암호/DB를 사용하지 않았다.

업로드 검사는 인증 정보 URL 거부용 합성 테스트 문자열1개를 지적했다. 거부 검사는 유지하고 메모리에서 URL을 구성하도록 수정했다. 검사 규칙을 완화하거나 실제 자격증명을 숨긴 것은 아니다. 비공개 원문·.env·.local·검사 결과는 Git 제외 상태다.
