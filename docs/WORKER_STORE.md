# 제작 작업 저장·예산·취소 연결

2026-10-04 로컬 구현과 격리 검사 결과. 운영 Supabase에 적용하지 않았고 운영 제작실의 모의 실행을 바꾸지 않았다.

## 구현

`supabase/proposals/studio_worker_v1.sql`은 v2와 예산 SQL 이후에 적용할 별도 검토안이다. `worker_execution_enabled()`는 기본 false이며 예산 enabled도 별도로 true여야 접수·실행이 가능하다. 기존 mock 작업 행은 변환하지 않는다. 새 real 작업에만 입력 검토 ID, 정확한 입력 바이트의 해시, 작업 ID, GitHub 실행번호/시도, 예산 예약을 연결한다. worker_runs/worker_evidence에는 RLS를 켜고 anon/authenticated의 조회·쓰기·함수 실행을 허용하지 않는다.

검토된 입력을 접수할 때 작업·메시지·실행 정보와 전체 작업 예산을 한 트랜잭션에서 저장한다. 예산/동시 한도 초과 시 작업 행까지 롤백한다. 같은 사용자 요청 ID와 같은 입력은 기존 작업을 반환하지만 입력이나 검토 ID가 달라지면 거부한다. 입력 검토 ID는 **신뢰된 서버의 실제 검토 절차가 발급해야 하는 참조**이며 UUID 하나의 존재만으로 자료의 AI 처리·공개 권리가 증명되는 것은 아니다. 이후 [입력 확인 UI/API와 DB 결합](INPUT_REVIEW.md)을 로컬 구현해 새 worker 행에는 실제 확인 기록을 요구하도록 보완했다. 운영 적용과 실제 dispatch는 아직이다.

GitHub 실행번호는 검증한 dispatch 결과를 받은 서버가 결합한다. claim은 한 번만 성공하고 동일 실행의 재점유나 GitHub 재실행 attempt 2는 새 API 호출을 시작하지 않는다. 실행번호를 전달하는 것 자체는 인증이 아니다. 후속 [작업자 인증 API](WORKER_AUTH.md)에 GitHub OIDC 서명 검증, 저장소 ID·workflow/ref/실행번호 매칭과 DB 토큰 재사용 차단을 로컬 구현했다. 실제 Actions 토큰 연결은 아직이다. Supabase service_role 키는 관리 서버에만 두며 생성 코드나 검사 job에 전달하지 않는다.

`automation/runner/worker-store.mjs`는 DB 저장소를 기존 파이프라인의 authorize/claimRun/checkpoint/record에 연결한다. RPC마다 10초 전송 제한과 영수증 확인을 적용한다. 공급사 응답 원문과 후보/검사/검토 기록은 비공개 evidence에 보존하며 공개 Actions 로그로 출력하지 않는다. 작업당 기록 40개·총 16MB, 개별 기록 2.1MB 상한이다. 같은 이벤트 ID의 같은 본문만 재전송할 수 있고 변경된 본문은 거부한다. 저장 응답을 잃었다고 자동 재전송하거나 API를 다시 호출하지 않는다.

최종 후보는 후보→실행 검사→검토 순서, 같은 후보 해시·시도 번호·검사 해시, 과학/학습/교육과정/교과서·실행/계약 검사 결과가 모두 맞아야 `awaiting_approval`로 이동한다. 승인·릴리스 행을 만들거나 게시하지 않는다. 새 후보 이후 이전 검토를 재사용하거나 미실행 항목을 통과로 승격할 수 없다.

취소가 먼저 확정되면 다음 호출 예약과 완료 전이가 막힌다. 마지막 확인 직후 취소와 완료가 경합해도 DB에서는 취소가 우선하며 승인 대기로 넘어가지 않는다. 알려진 사용량은 정산하고 미사용 예약만 반환한다. 과금이 불확실한 호출이 있으면 작업을 끝내도 자금과 프로젝트 실행 슬롯을 유지한다. 이 상태의 실제 청구 대조·명시적 복구 기능은 아직 추가해야 한다.

## 실제 검사

`npm.cmd run test:studio`: **76/76 통과**. 새 worker DB 검사 9개에는 기본 차단, 권한, 기존 mock 작업 행 보존과 기존 RPC 전이, 원자적 접수/예산, 실행번호 결합/중복 점유, 취소, 기록 재전송, 버전이 다른 검토 거부가 포함된다. 통합 사례는 PGlite의 실제 SQL과 모의 공급사 응답으로 다섯 역할 호출→정산→비공개 증거 8개 저장→사람 승인 대기까지 실행했다. 실제 유료 호출이나 과학 검토가 아니다.

`tests/studio/worker-postgres17.mjs`: **실제 PostgreSQL 17의 독립 물리 연결 경쟁 9/9 통과**. 최종 실행 21:53:42~21:53:57 KST, 127.0.0.1:55443. 각 사례에서 선행 트랜잭션의 잠금을 유지하고 다른 연결이 실제 Lock 대기에 들어간 것과 차단 PID를 관찰한 뒤 커밋했다. RPC 실행 주체는 비슈퍼유저 service_role이었다.

| 선행 → 후행 | 결과 |
|---|---|
| 다른 소유자의 접수 → 접수 | 두 번째 PT423, 프로젝트 전체 동시 1건 |
| 작업 점유 → 같은 작업 점유 | 첫 번째만 claimed=true |
| 대기 작업 취소 → 점유 | cancelled 유지, claimed=false |
| 점유 → 이전 버전의 취소 | PT409, 갱신된 버전으로 다시 취소 가능 |
| 실행 취소 → 후보 완료 | cancelled, 승인 대기로 전이하지 않음 |
| 실행 취소 → API 비용 예약 | PT409, 새 예약 없음 |
| API 비용 예약 → 실행 취소 | 예약 금액 보존 |
| 사용량 정산 → 종료 | 발생 비용 보존, 나머지 예약 반환 |
| 과금 불확실 종료 → 늦은 정산 | PT409, 불확실 자금/슬롯 유지 |

최종 비공개 증거: `.local/worker-pg17-fd182d18647049a1b0eabb5aad1b20ef/result.json`. 앞선 8사례 실행도 별도 폴더에 보존했다. 최종 보고서의 4개 SQL 해시와 현재 파일 일치, 서버 정상 종료, postmaster.pid 없음, 임시 평문 암호 파일 제거, 검사 루트의 현재 사용자/SYSTEM 전용 ACL을 확인했다. 검사 전용 암호만 DPAPI 보관했다. 운영 암호·환경파일·DB를 사용하지 않았다. 전체 검사 180초, SQL 15초·잠금 10초, 프로세스/정리 제한을 적용했다.

잠금 순서는 예산 정책→필요 시 교사/대화→작업→실행 행으로 통일했다. [PostgreSQL 17 잠금 문서](https://www.postgresql.org/docs/17/explicit-locking.html)를 참고했다. 입력/기록 해시는 확장 설치 없이 [기본 SHA-256·UTF-8 변환 함수](https://www.postgresql.org/docs/17/functions-binarystring.html)를 사용한다.

## 남은 연결

후속 인증/API 구현 이후 전체92개와 실제 PostgreSQL 두 연결 경쟁11개가 통과했다. 위76개/9개는 앞선 실행 기록이다. 최신5개 SQL의 검사 결과와 실제 서버 응답 증거는 [WORKER_AUTH](WORKER_AUTH.md)에 기록했다.

운영 migration과 gate 활성화, 실제 GitHub dispatch/OIDC 발급 토큰 연결, 입력 공개 범위·자료 권한 검토 UI, 키 없는 생성 코드 검사 환경, 승인/게시/게시 확인은 아직이다. 실제 API 키도 준비 여부 답변 대기다. 지금의 통과 결과를 실제 사용자 입력부터 게시까지의 종합 성공으로 기록하지 않는다. 공개 업로드 승인을 요청한 기존40개 파일의 스테이징에는 이번 파일을 추가하지 않았다.
